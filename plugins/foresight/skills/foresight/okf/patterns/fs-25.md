# FS-25 · Errors swallowed, conflated or silently defaulted

Error handling collapses distinct failure classes or hides them: 4xx treated like transient 5xx, a generic isError triggering logout, config errors surfacing as 500, IntegrityError instead of 400, only top-level detail read so field errors vanish, fire-and-forget mutations dropping 400s, silent fallbacks (resolver defaults, a ?? b, dev mock on any error, 'non-fatal' config set). The UI or report looks fine while the real failure disappears. On mobile a boot gate's .catch only logs, so its readiness flag is never set and the app freezes on the splash, and an idempotent 'already applied' response arrives on the same rejected branch as a real failure.

**Triggers**
- try/except or catch around external calls or mutations with a single broad fallback
- code branches on isError/non-2xx without inspecting the status or error code
- a form or toast shows one generic message; a mutation called without await/catch
- a ?? / or-default / fallback-to-fixture on a value that is persisted or user-visible
- a retry loop around an unrecoverable input; a CI cache miss that silently falls back to a slow full build; try/except around ledger posting in save()
- a readiness flag set only inside .then() with a .catch that only logs; an async redeem/apply action with more than one success-like outcome; an env-prefix resolver that returns None when its env var is missing; an email/SMS send wrapped in log-and-continue
- a catch block issues ROLLBACK or other cleanup before rethrowing
- scripted API writes (curl/POST/PATCH) whose output is redirected to /dev/null or never parsed

**Guards**
- Test a mocked 400 with field errors and assert the field message renders; test the shared error helper against every DRF body shape
- Surface 4xx distinctly from 5xx/timeouts and map domain/config exceptions to explicit statuses in the same PR
- Await persisting mutations, revert optimistic state and toast on rejection
- Make resolvers/fallbacks raise under test, and read config back after setting it
- Force init to reject in a test and assert the UI reaches an error/retry state; enumerate backend response codes and map each to a UI outcome; make config resolvers raise at boot on missing inputs; alert, not only log, on provider auth/4xx failures
- Wrap cleanup inside error handlers in its own try/catch, log its failure, and always rethrow the original error
- Read and assert every API write response (id, status, changed field) and print it; a write whose response was not read did not happen
