# FS-100 · Async job result or system write applied without a current-state or supersession check

Bot/webhook callbacks, retried jobs and background subsystems write their result onto an entity without re-checking what it is now. A late callback mutates rows after the entity moved on, a retried job overwrites a newer version of a versioned aggregate, a completion writes a baseline from the snapshot captured at dispatch, and one subsystem overwrites another's blocked-reason field. Serial tests deliver each event once and in order, so late, duplicate and out-of-order arrivals corrupt state only in production-like runs.

**Triggers**
- a bot/webhook callback endpoint or async job completion that writes shared rows and can arrive late, twice or after a retry
- a versioned aggregate or review baseline written from data captured at dispatch time
- several subsystems (watchdog, budget, bot failure, user hold) writing one status or reason field
- a locally persisted draft restored over a field other users can save, or a tracker fed by both launch and resume events

**Guards**
- Capture a supersession token (job id, version, content hash) at dispatch; at apply time re-read the entity under a row lock and drop the result if status, version or hash no longer matches
- Define a precedence order for shared status/reason slots and only overwrite a lower-precedence value
- Test late, duplicate and out-of-order callbacks, and a completion arriving after a newer job was dispatched, asserting the newer state survives
- Store the base version with a draft and warn or drop it when the server version moved; key trackers by entity id so a resume event applies idempotently
