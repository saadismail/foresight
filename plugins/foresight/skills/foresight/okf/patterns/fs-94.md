# FS-94 · CI fan-out multiplies load on a shared resource the single job never stressed

Splitting a job into a matrix of shards, or adding runners, multiplies whatever each job does. An auto-sized worker pool (xdist -n auto) in every shard oversubscribes the same cores. Per-job platform API calls (CreateArtifact, a setup action's version fetch) hit known-flaky endpoints N times at once. A flake fix tuned at the old concurrency fails again at the next increase. Per-shard timings look fine while wall clock and reliability get worse.

**Triggers**
- a CI job gains a matrix/shard fan-out, or the self-hosted runner count increases
- the sharded suite already parallelizes internally (pytest-xdist -n auto, jest workers)
- steps after the test run call platform APIs (artifact upload, cache save, tool download) that the repo already notes as flaky
- a concurrency-triggered flake was 'fixed' by tuning an input on the third-party action that makes the network call

**Guards**
- Cap per-shard workers at cores / shards (or keep one shard until shards run on separate hosts) and measure end-to-end wall clock before merging, not per-shard time
- Audit every step after the test run for platform-API calls now made N times concurrently; add retry or continue-on-error to non-authoritative artifact uploads, keeping the job result authoritative
- At each concurrency increase, re-run the scenario that flaked before, and prefer removing the network dependency (a host-provisioned tool) over tuning action inputs
