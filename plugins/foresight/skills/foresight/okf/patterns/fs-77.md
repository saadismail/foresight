# FS-77 · Gated app flow (onboarding, paywall, restore) kept consistent only by navigation order

Onboarding, paywall and navigation-restore behavior is encoded as navigation rather than as state each screen checks: a route allowlist in a guard, 'we never navigate here when subscribed', one completion side effect repeated per exit path, a saved stack replayed with router.push. A new entry route missing from the allowlist bounces users back, a new exit path skips marking onboarding complete, a paywall renders for an already-Pro user reached through skip or the back stack, and a cold-start restore replays every saved frame while an unguarded state listener re-persists it.

**Triggers**
- adding a screen or entry point reachable from inside a gated flow (onboarding, auth wall, paywall)
- adding a new way to exit a wizard step alongside the existing purchase/continue paths
- a paywall/pricing screen reachable by more than one path (wizard, deep link, back stack)
- a nav-state restore effect issuing several router.push/replace calls while a state-change listener persists navigation

**Guards**
- Write a router-guard unit test asserting the new route is not redirected in each incomplete-flow state before wiring the UI entry point
- Route every exit of a gated step through one shared completion function (for example completeOnboardingStep()) and test each exit
- Make gated screens self-guard at render time on the real state (effective_plan, onboarding_completed_at) instead of relying on navigation
- Cap restored navigation to [tab, leaf] and suppress persistence listeners while a restore replay runs; test the back-press count after a cold start
