# FS-56 · Ledger-wide change verified only where it was aimed

A posting-rule, polarity, exclusion or account_type change, or a rebuild/cleanup run, is checked only on the day, location or report that motivated it. The same computation feeds other days, periods, the balance-sheet footing and closed fiscal years; cleanup flags without date scoping, single-day rebuilds of multi-day entities, and recipes reused on a structurally different entity regress previously balanced data outside the target, which is found later as a 'new' imbalance.

**Triggers**
- changing an account/polarity mapping, an exclusion from net income, or an account_type on existing data
- running a rebuild/resync/--clean-dangling over a subset of days, or reusing a script validated on another entity
- a rebuild range that includes closed periods or unverified/junk entities
- the flagged day involves a cross-location bank transfer or another entity a generic rebuild doesn't handle

**Guards**
- Snapshot per-day balances (day_delta walk) and period-end totals for the whole affected range plus adjacent and closed periods, apply, then diff against the snapshot before calling it done
- Measure balance-sheet footing on a couple of real locations with data in the category before changing a shared aggregate
- Read the tool's documented scope and each flag's implementation (is it date-scoped?) before running; rebuild contiguously from a known-balanced opening date
- Gate posting of unverified/junk entries and closed periods behind explicit checks; re-check day_delta immediately after each rebuild
