# FS-41 · Client derives answers from one page of a paginated list

The FE filters, sorts, groups, counts, slices or resolves labels over whatever rows it happens to have fetched (one page, .results only) instead of asking the backend. Correct on seed data that fits one page; silently wrong once real data spans pages.

**Triggers**
- a search box or group/sort option whose query hook has no matching backend param
- .filter/.sort/.slice/.find applied to query results, or a KPI computed from the list held in state
- a label resolved by looking up an id in another cached list, or a :key route resolved via fuzzy search results[0]
- response.results consumed without count/next
- an audit of 'all affected items' built from one page of a CLI/API listing
- a list that combines multi-select or an empty state with infinite-scroll appends

**Guards**
- Grep new list code for .filter(/.sort(/.slice( on API results and send search/sort/group as query params
- Denormalize display fields (key/title) onto the serializer and add exact-match lookups
- Back KPIs with server aggregates and run the e2e with more rows than one page
- Reconcile before/after totals exactly when auditing via a paged listing
- e2e: select rows, scroll to append the next page, and assert selection count and empty-state text stay correct
