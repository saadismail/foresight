# FS-110 · Admission gate decides on a load sample that lags admitted work

A gate admits heavy jobs (parallel agent lanes, test runs, builds) when one instantaneous sample of CPU idle or load looks healthy. Jobs admitted moments earlier have not ramped up yet, so the sample still reads idle and several jobs pass together; when they ramp at once the host thrashes (load far above the core count, agents stall). Background OS work such as file indexing of new checkouts adds to it. Each admission looked correct when it was made.

**Triggers**
- an admission or throttle gate that checks current CPU idle, load average or free memory once before starting each job
- jobs that take minutes to reach peak usage (dependency install, server boot, test-suite ramp)
- several queued jobs waiting on the same gate

**Guards**
- Count admitted-but-ramping jobs against the budget (a fixed reservation per admission for its ramp window) instead of trusting the live sample alone
- Admit one job at a time with a cooldown about as long as a job's ramp, decide on a sampled window rather than one reading, and keep a hard cap on concurrent heavy jobs
