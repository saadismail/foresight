# FS-52 · Named-account get_or_create keyed on account_type forks duplicates as type strings drift

Chart-of-account rows are resolved or auto-created by get_or_create/update_or_create on (name, organization, location, account_type[, is_department]). When code changes the account_type a posting constant selects, a sibling caller omits account_type, legacy rows carry another spelling, or a merge leaves the keeper with a different type, the lookup misses and forks a live duplicate (or fails NOT NULL on create). Imports without dedupe and create/restore/replication paths recreate merged-away accounts, and retyping an account silently reclassifies every historical leg.

**Triggers**
- get_or_create/update_or_create on a chart-of-accounts model whose lookup kwargs include account_type or other classification flags
- changing the account_type string a posting constant, service or verify command uses
- sibling posting functions calling the same account lookup helper with different parameters
- merging or retyping accounts, or a bulk update into a column that is part of a unique constraint
- a create/restore or corp-replication path that matches by (name, type)

**Guards**
- Put only identity fields (organization, location, name) in the lookup and classification in defaults=; test with a pre-existing same-name row of another type and assert no second live account
- Pair every account_type constant change with a data migration that retypes existing same-name rows across every location tier, and patch recurring jobs' lookup keys together with any merge
- Dry-run a collision query before bulk updates into unique-constrained fields and route twins to a merge path
- Block or warn on account_type changes for accounts with posted legs (use a dated reclass entry); before merging across types, confirm both map to the same report bucket and polarity
- Route create/restore/replication through one merge-aware helper that checks the account merge log
