# FS-48 · Money sign, credit polarity and precision decided ad hoc in several layers

Direction of money is encoded more than one way (signed amount, abs(amount) plus a credit flag, per-path sign constants) and normalized in several layers: Transaction.save() force-sets credit for source types missing from a hand-maintained allowlist and auto-flips negative amounts, report code applies abs() after Sum(), filters use value < epsilon, dedupe keys use unsigned amounts, balance-sheet buckets recognize only listed account_types, and amounts live in FloatField or float accumulators mixed with Decimal. The positive, one-direction happy path balances; refunds, negative corrections, the other direction or a new source/account type post on the wrong side or vanish.

**Triggers**
- a service sets an explicit credit flag, or passes a possibly negative amount, for a new or changed source_type
- a new source_type or account_type constant is introduced (save() credit/sign allowlists, BS/P&L bucket constants)
- abs(), '< 0.01'-style epsilon filters, or an unsigned amount in an aggregate, dedupe key or skip guard
- a two-direction entity (disburse/receive, debit/credit) gets a validation or aggregate on one side only
- FloatField money columns, float accumulators in scripts, output_field=DecimalField on a Sum/Window
- a reviewer finds a polarity defect and downgrades it because it matches legacy behavior

**Guards**
- Test positive, negative and zero amounts for every source_type and both directions, asserting the persisted row's signed amount and credit flag after save(), not the value passed in
- When adding a source type or account type, grep every allowlist and bucket constant (a transaction model's save() credit/sign lists, the asset/liability/other-expense type buckets) and add it; prefer inverting defaults so explicit flags win
- Apply sign handling per row before aggregation, never abs() after Sum(); write an additivity test (full range == sum of sub-ranges) with mixed-sign rows
- Use abs(x) < eps for near-zero checks, keep sign/direction in idempotency keys, and mirror every one-direction validation with the opposite-direction test
- Store and sum money as Decimal (Cast inside the Sum/Window), start accumulators at Decimal('0'), and treat a legacy-matching polarity defect as blocking
