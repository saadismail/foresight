# FS-60 · Read after write or guard read routed to a lagging replica

Production routes ORM reads to a read replica (ReplicaRouter/PinningReplicaRouter, USE_REPLICA=1) while tests and dev run one database. A read of a row just written in the same request or script, a lazy FK re-query, a soft-delete cascade walker, a bulk sync re-reading its output, or a guard feeding a permission/delete/merge decision hits the replica before replication, so it sees stale or missing rows, raises false integrity errors or makes a stale decision. Fixes pin the quoted line but not the other reads feeding the same decision.

**Triggers**
- a handler, script or bulk sync writes and then reads the same or related rows
- a read feeds a permission check, lock, delete/merge guard, or the verification of a write
- the file already uses .using('default') on neighbouring reads
- third-party code (soft-delete cascade, related managers) reads without the router hint

**Guards**
- Pin every read that follows a write or gates an irreversible decision to primary (.using('default'), select_related on the write connection), tracing the full data flow into the guard
- Run delete/merge/permission tests with USE_REPLICA=1 or a replica-simulating router, and assert the active router class in ops scripts before trusting a verification read
- When fixing one replica-lag finding, grep for the same write-then-read pattern org-wide instead of patching one call site
