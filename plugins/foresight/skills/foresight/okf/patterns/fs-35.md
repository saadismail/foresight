# FS-35 · Test depends on uncontrolled shared data or unrealistic setup

Specs and fixtures lean on persisted shared e2e data or on setup that doesn't match production: seeded workspaces archived by other specs, per-user preferences shared across specs, rows accumulating across runs, DBs reused across branches, a real browser profile leaking in, actors without memberships, filter values that don't isolate the case, destructive steps that hit invariant guards. Results depend on run history, not on the code.

**Triggers**
- a spec mutates or depends on a shared seeded workspace/project/board instead of creating its own
- a seed helper with fixed dates/names on a DB that persists across runs or branches
- a global per-user preference written by one spec and read by others
- a test actor created ad hoc without membership/role, or an app launched without a fresh profile
- an e2e spec or seed script inserts rows by direct DB access with no teardown or prune step; a re-runnable seed that only issues INSERT ... ON CONFLICT DO NOTHING
- a negative/absence fixture names a real entity (subdomain, vendor) that ongoing work is onboarding; seeding a 'connected' flag that gates a live external API call; a browser session carried across dev-server restarts or earlier OAuth attempts
- an exact count asserted on a shared scratch/seed project; a spec that creates its own project but still references the shared seed project id; a seed helper that silently no-ops when the board already has data
- a narrowing search term built from short numeric or common tokens against word-split backend search; extra browser contexts created while the config sets use.storageState
- re-running a pipeline or lab run (document ingest, import) into the same project or tenant that still holds an earlier run's output

**Guards**
- Create throwaway entities per spec through API/seed helpers and clean up in try/finally
- Use unique generated values for constrained fields, and recreate the e2e DB when switching worktrees/branches
- Compute expected results from the seed data inside the test, and give test actors real memberships
- Reset persisted preferences and pass a fresh userDataDir per launch
- Tag every e2e-created row with a fixed marker (prefix or is_test flag) at creation, delete by exact match in teardown, and assert row counts stay stable across two consecutive runs
- Make seeds converge: remove rows outside the intended set before inserting, and test by injecting a drifted row and re-seeding
- Use synthetic reserved values for 'not yet supported' fixtures; default seeded integration flags to the disconnected state; pin SECRET_KEY in the local env and use a fresh browser context after restarts or earlier auth flows
- Create a throwaway project per spec for exact-count or config-writing assertions and grep specs for writes on shared seed ids
- Use unique alphanumeric tokens that cannot appear in keys or timestamps; create extra-user contexts with an explicit empty storageState and pass the user's own workspace slug, asserting the signed-in user first
- Test seed commands by running them twice and asserting row counts unchanged
- Create a fresh project per run, or assert the target is empty before starting, and compare the result against the run's own inputs
