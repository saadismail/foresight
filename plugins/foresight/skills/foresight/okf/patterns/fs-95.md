# FS-95 · Worker-pool early-abort semantics assumed from the context manager

All work is submitted up front to a `with ThreadPoolExecutor(...)` block, and the code or a comment says a failure aborts the rest. But `__exit__` calls shutdown(wait=True) without cancel_futures, so every queued future still runs. Even with cancel_futures, a freed worker can grab one more queued item, so a test pinning an exact started-count flakes or fails deterministically.

**Triggers**
- all work submitted to a `with ThreadPoolExecutor`/ProcessPoolExecutor block while a requirement says the first failure should stop the remaining work
- a test or brief specifying an exact count of tasks started before cancellation
- replacing a sequential loop that stopped at the first error with a pool

**Guards**
- Call pool.shutdown(wait=True, cancel_futures=True) in a finally (or submit lazily), and test with more tasks than workers where task 0 raises, asserting started < total
- Assert the guaranteed invariant (max in flight, started < total) rather than an exact count, and run the test 20+ times before trusting it
- Compare how many tasks run on failure with the sequential loop being replaced
