# FS-07 · Parallel code paths for one operation diverge

The same operation or number is implemented in more than one place (single vs bulk, API create vs seed/import/duplicate, preview vs apply, immediate vs polled dispatch, list vs detail serializer, per-row cell vs summary tile). A guard, side effect, lock, scope filter or display rule added to one path is missing or different in the others, and tests cover only the primary path.

**Triggers**
- adding a guard, side effect, lock or scope filter to a create/transition/update method
- a bulk, seed, import, duplicate or management-command path exists alongside the primary one
- a preview/count endpoint or summary tile computes the same quantity as the action or list next to it
- a requirement says 'applies to all X' but X gets wired one input or one surface at a time
- Django bulk_create/bulk_update/queryset.update() on a model whose save() or pre_save signals carry side effects (ledger sync, audit stamping, auto_now)
- single-match vs multi-match handlers, or a required field/alert added to one caller of a shared function
- adding a new state/segment variant to a list row that renders a different icon per variant
- a feature adds a model or file field that a page renders while a seed/demo script builds the same data separately; a multi-write service function called from both a view (ATOMIC_REQUESTS) and a shell/command/task
- adding a second resolver for the same binding kind next to one that already handles scope/shadowing
- a new subtype, hold/lock state or rollout flag that must be protected across a module whose write routes (callback, retry, upload, generic CRUD, bot endpoints, service callers) all reach the same downstream path
- a bulk move/visibility/delete endpoint added next to single-item actions that write audit entries
- a test harness gains a new execution mode (per-worker DBs, shards, pooled seeding) while helpers resolve their own DB URL, interpreter or seed flags
- a scrub, profile or sandbox applied where an artifact or CLI argv is first built, while other writers or launchers (resume and follow-up turns, group copies) build their own

**Guards**
- Grep every path that creates or mutates the model (views, bulk, seed, import, duplicate, commands) and route them through the same service method
- Extract the shared rule into one function used by preview and apply; assert preview == outcome and summary == sum(rows)
- Add one test per path for any new guard or side effect, and decide explicitly which side effects bulk/import paths must fire
- Grep bulk_create/bulk_update/.update( on affected models and call the same sync explicitly (include auto_now fields in bulk_update); add a parity test for every sibling entry point
- Give every variant the same fixed-size wrapper as its siblings and compare alignment in one screenshot
- Extend the seed for every demo account and state in the same change, generate seeded files through the product's real builder, and add a reconciliation test; apply the transaction.atomic decorator on the service function itself and test it by calling it directly
- When adding a sibling resolver, reuse the existing one's scope/shadow guard and test the shadowed case on both
- Enumerate every write entry point that reaches the guarded state (grep URL routes and service callers), put the guard at the shared service/write entry rather than per endpoint or at a later transition, and add one test per entry point
- Test that each bulk action writes one audit row per touched item, exactly like the single-item path
- Resolve DB name, interpreter and seed routing in one shared harness helper used by every fixture and subprocess, and smoke every mode (1 worker, N workers, pool) asserting the DB each worker actually used
- Grep every writer of the artifact and every argv builder, route them through the one function that applies the scrub or profile, and test each launcher's output
