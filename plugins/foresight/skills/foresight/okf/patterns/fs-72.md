# FS-72 · Bottom clearance (safe area, tab bar, keyboard) applied zero times or twice

Bottom spacing in React Native comes from several layers that may already reserve it: React Navigation shortens scenes above a non-absolute tab bar, iOS ScrollView contentInset and paddingBottom both add space, useSafeAreaInsets must be added in every layout branch, and on Android edge-to-edge (Expo SDK 54 default) adjustResize is a no-op so KeyboardAvoidingView never lifts a pinned footer. Code adds its own padding without checking which layer already handles it, or drives margin from a raw keyboard-height listener with no clamp. It looks right on the device checked and leaves gaps, home-indicator overlaps or hidden Save buttons elsewhere.

**Triggers**
- a style object branches (inline/modal/full-screen) and only one branch adds insets.bottom
- a shared hook adds tab-bar height as padding, or a ScrollView sets both paddingBottom and contentInset.bottom
- a pinned footer relies on KeyboardAvoidingView in an Android edge-to-edge app without react-native-keyboard-controller
- layout margin driven directly by a Keyboard event height
- a form screen with text inputs uses a vertically centred or flexGrow contentContainerStyle

**Guards**
- Before adding clearance, render with padding 0 to see what the navigator and safe area already reserve; pick one mechanism per screen and grep for co-occurring paddingBottom + contentInset.bottom
- Add insets.bottom in every layout branch of a bottom-pinned control
- On Android edge-to-edge use react-native-keyboard-controller (or explicit keyboard padding) and screenshot with the keyboard open on a real Android device
- Clamp keyboard-derived heights to a fraction of the window height and reset them on keyboardDidHide and when AppState leaves 'active'
- Top-align input forms (top-aligned ScrollView plus KeyboardAvoidingView); a centred layout has no overflow for any avoidance technique to reveal
