# FS-66 · Session-scoped cloud or CLI credentials assumed still valid

AWS SSO tokens and CLI OAuth logins expire within hours, and long sessions, sub-sessions and bench runs inherit the same expired state. Investigations, downloads and tunnels start without an identity check and fail mid-flight, sometimes after partial work, and the same expiry recurs after each multi-hour gap.

**Triggers**
- starting remote diagnostics, an SSM/tunnel session, a cloud download or a local bench run
- a multi-hour gap since the last cloud command in the session
- spawning a sub-session that inherits local CLI auth
- an admin task starts with gcloud compute ssh or other gcloud calls under an org policy that forces periodic interactive reauth
- a gcloud scp/ssh production write late in a long session
- a merged PR's deploy step queued hours after the gcloud login in the same agent session

**Guards**
- Run a cheap identity check first (aws sts get-caller-identity, CLI auth status) and ask the user to re-auth up front if it fails
- Re-check at the start of every task that opens a new tunnel/SSM session, and short-circuit dependent runs on the first auth failure instead of retrying each blind
- Keep a documented fallback path (SSH key) for remote access
- Check gcloud auth validity first and surface reauth immediately; prefer a service-account identity for headless admin scripts
- Run gcloud auth print-access-token before staging files and again right before the write
- Run gcloud auth print-access-token right before any queued deploy step and use a deploy-scoped service account instead of a personal OAuth session for automated deploys
