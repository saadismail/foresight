# FS-81 · Next.js build output (.next) shared between dev and e2e, or served stale by next start

A Next.js app's dev server and the e2e or verify harness write the same default distDir (.next), and the Playwright webServer runs `next start` (often with reuseExistingServer) against whatever build is there. A concurrent `next build` deletes chunks from under the running dev server (MODULE_NOT_FOUND on vendor-chunks, ENOENT on app-build-manifest.json, 500s), `next start` keeps serving a baked build with no watcher so edits never appear, and status-only health checks keep returning 200. The failures look like bundler bugs or real regressions, so fixes are made against the wrong build.

**Triggers**
- a Next.js app whose dev server and Playwright webServer (or a verify build) both default to .next, with no per-purpose distDir
- the e2e webServer command is `next start` / start:e2e with no preceding `next build`, combined with reuseExistingServer
- intermittent MODULE_NOT_FOUND on vendor-chunks, ENOENT on app-build-manifest.json or 'Could not find a production build' while another agent's suite runs
- a monitor or health check that only curls routes for 200 on a shared dev port that another process can restart
- an e2e failure shows old copy or CSS right after a source change

**Guards**
- Give dev, e2e and verify builds separate distDirs through an env var (for example NEXT_DIST_DIR=.next-e2e) from the start
- Make the e2e webServer command build before it starts, or set reuseExistingServer: false when validating a rendering change; on any stale-looking result kill the port and rebuild before re-running
- Check the serving process's command line (next dev vs next start) and prove live reload by adding and then removing a throwaway route, not by a 200
- Before blaming the bundler for MODULE_NOT_FOUND/ENOENT, check .next artifact mtimes and which process last wrote them
