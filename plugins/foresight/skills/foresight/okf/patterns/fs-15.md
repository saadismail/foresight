# FS-15 · Producer and consumer of the same data disagree

Two sides of one data flow are defined independently and drift: FE/BE/daemon field names and envelopes, a mock's params vs the real filter, OAuth scopes in console vs code, enums duplicated across files, write-path HTML vs read-path renderer, sanitizer allowlists vs newly emitted markup, imported records vs what the read path filters on. Each side passes its own tests; only a round trip exposes the mismatch.

**Triggers**
- a feature spans FE + BE (+ worker/daemon), or the FE merges ahead of its BE slice
- content written into a rich-text or sanitized field, or new tags/attributes emitted
- the same list of values (scopes, verbs, options, params) maintained in more than one file or system
- an import/migration creates records the UI will display
- a filter validates against a label map the tagger doesn't share; instructions and a helper script share a numeric parameter; parallel FE/BE agents assume a URL prefix
- seeding or backfilling rows by shell script for an organization/workspace-scoped model that a mobile client pulls
- a business status shown on several screens or clients (attendance Late/Absent) is reported wrong while only one client repo is open
- a dataclass with to_dict/from_dict gains a field; hand-authored fixtures for a scorer that treats an unknown key as a silent non-match
- FE and BE lanes or fix waves running in parallel against one contract; the FE reading a field the frozen contract doesn't have yet
- one endpoint emits references (links, packets, manifests) that another endpoint resolves or validates
- the same figure computed on server and client (rounding, percentages)

**Guards**
- Write a round-trip test: produce via the real producer (exact FE payload keys, the editor API), then read via the real consumer (GET, read-only renderer)
- Derive enums/options/scopes from one source of truth (schema endpoint, catalogue module) instead of duplicating
- Assert every FE model field is populated from a realistic API fixture; map DRF envelopes in transformResponse
- When emitting new markup, check the sanitizer allowlist and renderer parity on every pipeline the field passes through
- Set every scoping field the client read path filters on (organization_id) and confirm one seeded row appears end to end in the app before debugging sync
- Grep where the flag is SET (not just read) across the server and every client, and fix the decision in the layer that owns it
- Round-trip every new field (to_dict then from_dict) in a test, and run every new fixture through the real scorer/consumer, not only the producer-side diff
- Generate TS types from the OpenAPI schema or add a parity test (codes, fields, enums) so drift fails CI; amend the contract before the FE reads a new field
- Share one visibility/liveness filter between the endpoint that emits a reference and the one that resolves it, and test that every emitted reference resolves
- Compute shared figures once on the server and send them; never re-derive with a different rounding rule
