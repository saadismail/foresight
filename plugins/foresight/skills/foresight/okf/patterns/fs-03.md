# FS-03 · Code written against an assumed interface instead of the real one

Code, fixtures, scripts, selectors or plan snippets are written from memory or by analogy (a sibling model, a similarly named component, a library's default DOM, a unit-test mock) rather than from the actual definition: response shape, model fields, route params, hook return type, primitive API (Radix vs base-ui), field units/semantics, rendered DOM. It looks plausible, often type-checks, and fails only at runtime or in the browser.

**Triggers**
- writing a parser, fixture or script against an endpoint without having printed one real response
- copying a pattern from a sibling model/component whose underlying type, import path or markup differs
- hand-building a route, deep link or e2e selector for a page not inspected this session
- a plan snippet calls a library API or hardcodes a URL/regex/selector with no source citation
- deriving a flag or scaling factor from an API field whose unit/semantics aren't documented
- an ad hoc prod script or fix guesses a manager name (all_objects vs global_objects), a status value, which model an API id belongs to, or which field the FE reads
- copying an RN sizing/style pattern (flexGrow: 0, fixed or percentage heights) from a component with different layout constraints; wrapping a third-party RN widget (phone input, picker) with custom overlay Views
- an <a href> download/print link to an API route in an app whose auth is a bearer token in localStorage; a storage OPTIONS dict copied from another backend (S3 to GCS); a custom leading icon added to an <input type=date>; seeding records at a non-default workflow status that a human will look for
- a plan or brief routes/filters at a downstream stage on a value (request host) computed and discarded upstream
- a brief or plan carries verbatim implementation code the implementer is expected to paste, written in parallel with other lanes
- a waitForResponse URL predicate written from the route name instead of the page's API slice endpoint
- PATCHing a field by its read name (assignee vs assignee_id) against an API that ignores unknown fields

**Guards**
- Print one real response, the model definition, the .d.ts signature or the router entry before writing code against it
- For e2e, inspect the real rendered DOM (roles, labels, testids) of the production component, never its unit-test mock
- Trace the route to the exact component file that renders the page before editing by filename
- Reuse existing URL/route builders and shared formatters instead of reconstructing them
- Before a data fix or new filter, pull one real record in the target state and grep the model's managers, the serializer and the exact FE filter/conditional it must satisfy
- Screenshot a new RN component, and any wrapped third-party widget against the library's own default render, before adding overlays or trusting copied sizing
- Fetch protected downloads with the Authorization header into a blob URL and make the e2e follow the link; instantiate the configured storage backend with its OPTIONS in a settings test; say which tab/filter shows seeded records, or seed at the status the default view shows
- Before writing a brief that routes on a value, grep the intermediate data model (CallSite) to confirm the field is carried and populated at that stage
- Treat plan code as a draft: grep each cited hook, type and API in the real codebase, run the RED test first, and apply the repo's size, tenancy and lock-order rules before pasting
