# FS-76 · Native capability added without its signing, entitlement, packaging or store-policy counterpart

A native permission, entitlement, system-store field or packaging option is added for a feature, but its counterpart outside the JS code is not updated: a provisioning profile pinned in exportOptions.plist predates new entitlements (Associated Domains, Sign in with Apple), Play requires a declaration for FOREGROUND_SERVICE_* permissions, writing CNContact.note needs a restricted Apple entitlement the Simulator doesn't enforce, and expo.useLegacyPackaging=false leaves no fallback when the arm64-v8a split is missing. Debug builds and simulators pass; export signing, store review, real devices or production crash reports catch it, often releases later.

**Triggers**
- a config plugin or AndroidManifest change adds a permission on Play's declared-permission list (FOREGROUND_SERVICE*, background location, exact alarms)
- adding an entitlement or capability while exportOptions.plist pins a named provisioning profile
- a native module writes Contacts/Calendar/Photos fields and has been tested only on the Simulator
- changing APK/AAB packaging (useLegacyPackaging, ABI splits, device targeting)
- the app requests a sensitive permission (location) and the repo keeps its own privacy doc of intended App Privacy label values

**Guards**
- Use automatic (Xcode-managed) signing for release export so entitlement changes regenerate the profile
- File the Play Console declaration in the same work item that adds a policy-gated permission, not at release time
- Check Apple's restricted-entitlement list for every system-store field written and smoke-test the write on a real device
- Inspect the built AAB/APK device targeting (bundletool) for every target ABI including arm64-v8a, and install on a real arm64 device with the configuration Play will serve
- Before every submission diff the live App Store Connect App Privacy labels against the repo's privacy doc field by field and remove declared-but-unused data types
