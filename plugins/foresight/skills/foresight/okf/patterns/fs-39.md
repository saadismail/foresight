# FS-39 · Parallel agents dispatched onto overlapping files or allocators

Work fans out to parallel agents/branches whose scopes overlap on one app's migrations, sequence numbers, shared helpers, components or singleton rows, or forks from a tip missing a sibling's finished work. Each branch is green alone; the merged tree has conflicting migrations, duplicate abstractions, IntegrityErrors, or specs asserting the other branch's placeholder.

**Triggers**
- about to dispatch parallel worktree agents that touch the same Django app, shared service file or component
- each branch will add a migration or claim the next sequence number
- a phase forked before its sibling phase merged, or a docs/wrap-up task running concurrently with implementers
- a forked/resumed session says background agents died
- parallel feature branches (not only agents) each add a migration off the same parent before landing on a shared stage branch
- parallel branches bump one global client schema constant (SQLite SCHEMA_VERSION) or add the next Django migration number
- a merge or conflict resolution inside a brace-structured file (CSS, JSON message bundle, TS API client), including one git reports as conflict-free; a long-lived or batch of feature branches merged into main that each touched models.py
- parallel worktree tickets that each bump one global version constant (EXTRACTOR_VERSION)
- parallel lanes each adding error codes, fields or enums to one shared contract module that the FE mirrors by hand
- an integration branch receiving lane merges while the base branch keeps moving; lanes deviating from a shared written spec

**Guards**
- Partition by file ownership; pre-assign shared helper names/owners and migration numbers, or plan a makemigrations --merge step
- Re-check the app's latest migration number against origin/staging immediately before merge
- Fork dependent phases from the merged tip and run docs/wrap-up last
- Re-run every touched spec on the fully merged tree before declaring the gate green; confirm the original coordinator is dead before relaunching
- Run makemigrations --check on the shared branch right after each merge and commit any merge migration a task depends on
- Before merging, read the target's current SCHEMA_VERSION / latest migration and take the next free number; treat every merge touching the constant as a conflict-check step
- After every merge, JSON-parse touched bundles, run the typecheck and the production build, and run makemigrations --check / showmigrations for every app with migrations before commit or deploy; resolve mid-object conflicts by re-inserting the added block into one side, never by concatenating both
- Reserve the next version value centrally before dispatch or serialize those tickets
- Lane 0: generate FE client types from the API schema, or add a code/field parity test, before lanes start adding to the contract
- Merge the base branch into the integration branch every wave and re-run every lane's scoped tests on the merged tree; record spec deviations in the spec as they happen
