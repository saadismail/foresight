# FS-106 · Test-result reporting collapses, filters or duplicates results so the run's verdict misstates what executed

Automated test results flow from a runner (JUnit, Playwright JSON) through a push CLI into a test-management ingest that maps many tests to one case. Each hop silently reshapes the verdict: ingest keeps one result per case (highest attempt, first on tie) so a failing test hides behind a passing one; a scoped run serializes every filtered-out test as skipped, and the UI counts skipped as complete, so 6 passed out of 182 reads as 100%; the scoped command runs one runner and misses e2e specs tagged to the same case; a wrapper pushes twice and creates duplicate runs; an evidence flag uploads nothing without its companion flag. Requirements turn green on evidence that does not exist.

**Triggers**
- many automated tests mapped to one test case or requirement (case-id tags, name patterns)
- a dedupe or winner-selection step in a result ingest keyed on attempt, order or timestamp
- a scoped or filtered test run (-t, --grep, tag filter) whose report is pushed as a run
- case tags spread across several runners (unit, API e2e, browser e2e) while the scoped command calls one
- a QA bot or CI wrapper that pushes results and may retry or be invoked twice
- progress or coverage percentages that count skipped as executed

**Guards**
- Collapse many results per case with worst-result-wins (failed > blocked > passed > skipped) within and across chunks, and test a case with one passing and one failing test
- Push only executed tests from a scoped run (or flag the run as scoped); keep skipped distinct from untested and exclude skipped from pass percentages
- Build the scoped command from every runner's specs tagged to the case and assert the executed count matches the tagged count
- Make result pushes idempotent on an external run id and assert one run per ticket round
- After a push, read the run back: totals, executed vs skipped, evidence count, and compare them with the runner's own summary
