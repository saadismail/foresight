# FS-40 · Invariant enforced in app code without a lock or DB constraint

Uniqueness, single-row, idempotency and state-transition invariants are enforced by check-then-act in Python (exists() then insert, delete+create, get_or_create/get on non-unique fields, time-window undo, whole-instance save()) without select_for_update, a DB constraint or update_fields. Serial tests pass; concurrent requests, retries, multiple workers or dirty shared DBs break the invariant. In multi-lane builds the lock order is assembled per lane and the harness checks only the first acquisition per kind, so hidden locks (FK KEY SHARE on a FOR UPDATE parent, unique-insert waits, late DELETEs, counter rows, helper-internal locks, re-locks of an earlier tier) deadlock, and each local deadlock fix introduces the next.

**Triggers**
- an exists()/get() check followed by an insert, especially with external I/O in between
- a worker/outbox table polled by more than one process, or a retryable create-then-persist
- save() on a model whose other fields are written asynchronously
- get_or_create or .get() on fields with no UniqueConstraint; new automatic assignment of a relation
- update_or_create/get_or_create keyed on one FK shared by two source types; an M2M modelling a single-owner relation; a timeout/reaper that mutates status after killing work
- a plan where several lanes add locked write paths to one subsystem, or a fix that adds a lock on an earlier-tier resource late in a transaction
- a transaction that also takes hidden locks: FK KEY SHARE checks against a parent held FOR UPDATE, unique-key INSERT waits, DELETE row locks late in the transaction, counter/sequence rows (max+1), row locks inside settle/refresh helpers, advisory locks, a re-lock of an earlier tier after a deeper one
- a threaded race/deadlock test with barrier or event park points, or a race test that asserts only 'no exception'
- a deadlock fix, or a lock-harness finding answered by broadening lock scope; rows read before the lock is held and written back after

**Guards**
- Back the invariant with a DB constraint and catch IntegrityError to return 400 or an idempotent 200
- Use select_for_update (skip_locked for workers) on the anchor row and save(update_fields=[...])
- Write a two-concurrent-request or kill-between-steps test, and run seeds twice
- Lane 0, before parallel lanes start: enumerate EVERY lockable resource of the subsystem (explicit row locks, FK KEY SHARE checks on locked parents, unique-key insert waits, DELETE row locks, counter/sequence rows, locks inside helper functions, advisory locks) into one global order table that every brief cites
- Build the lock-order harness once in lane 0: it records EVERY acquisition, not just the first per kind, flags any re-lock of an earlier tier after a deeper one, and runs inside every lane's scoped tests
- Ship a threaded deadlock/race test template in lane 0: two real threads (TransactionTestCase), park point placed BEFORE the lock under test, assert end-state consistency (no lost update, no stranded row), and confirm it fails with the lock removed
- Run every deadlock fix back through the harness and the threaded tests for EVERY entry point of the subsystem; in this codebase, fixes that reordered one pair or broadened lock scope introduced new deadlocks
- Read the rows you will write only after the lock is held; allocate per-parent sequences under a locked counter row or retry on IntegrityError
