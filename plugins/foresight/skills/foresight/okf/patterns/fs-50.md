# FS-50 · Live-data fix applied without re-detecting and confirming the exact target rows

Ad hoc cleanup and heal scripts run against production pick their rows with a heuristic (a notes pattern, one negative condition such as 'no CreditPayment linked', all locations and all history, an id read out of an error tuple), from a detection snapshot taken before concurrent resubmits or background jobs changed the data, against a DB target inferred from env vars, with a dry run that doesn't gate every side effect, and without capturing evidence first. Legitimate compensating rows get deleted, material amounts are auto-applied like trivial ones, and forensic questions can no longer be answered.

**Triggers**
- a script or --apply flag that deletes, strips or rewrites ledger/financial rows on a live DB
- the row filter is a text pattern, a missing-relation condition, or 'same shape as location X'
- the detection scan ran minutes or hours before the fix step, on a system users and jobs are writing to
- one combined apply spans many locations/entities, or the dry run wraps DB writes in atomic() while an external call (S3) runs regardless
- a 'who/when' forensic question is open about rows the fix will touch
- an irreversible cascade delete previewed from Django's Collector.data

**Guards**
- Print and confirm an identifying fact from the connected DB (row counts, a known location name) before any --apply
- Re-run the detector at the start of the fix step, check for concurrently running recon/backfill jobs, and re-query each target's live state (not just its id list)
- Scope the fix to the rows confirmed broken; spot-check known-good locations against the candidate filter and check each row's precondition (is the leg truly one-sided?) before bulk stripping
- Snapshot audit fields and the per-source diagnosis before any destructive step; print each target's business fields (amount, created_at, creator) before a hard delete
- Run per entity/location instead of one opaque batch, route deletions above a materiality threshold to explicit approval, and gate every non-transactional side effect on the same --commit flag as the DB writes
- Cross-check the preview against per-table row counts before and after the delete inside a rolled-back transaction; fast-deleted relations never appear in Collector.data
