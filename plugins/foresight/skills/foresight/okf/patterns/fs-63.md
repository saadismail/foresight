# FS-63 · Entity identity matched on a non-identifying attribute

Scripts, importers and pickers decide which real-world entity a row refers to by a display name, .first() of several candidates, or a (payee, amount, date) coincidence, while the data has names repeated across orgs/locations, several bank accounts per location, dangling duplicates from delete-then-recreate, and legitimate same-amount instruments. The opposite error also occurs: exact FK equality treats punctuation-variant duplicate payees as different entities. The wrong row gets linked, voided, skipped or created.

**Triggers**
- resolving a location, account or bank account by name or .first() in a multi-org / multi-account setting
- treating rows as duplicates because payee/amount/date match
- a match predicate in a reconciliation script that lacks the identity field (employee name, check number)
- guarding on FK equality in a domain with known near-duplicate master records
- a data migration dedups or groups by a business key without the tenant/repository id
- a reconcile/reindex step that runs per page or partition while row identity is unique per document; match keys that are mutable attributes or list positions
- output files or ids keyed on a value that repeats across sources (session id in two dirs) or derived from enumeration order while another artifact persists references to them

**Guards**
- Resolve by a unique key (id, check/invoice number) scoped by organization and location; when the input lacks one, require the column or flag every ambiguous row instead of taking .first()
- Query all candidates sharing the name across orgs and confirm against a reference point the user gave before creating or mutating
- Spot-check a known-unique row to confirm the match predicate discriminates; filter to currently linked rows (e.g. daily_entries__isnull=False) in models with dangling duplicates
- Ask before treating a same-amount/same-date record as a duplicate
- Include the tenant key in dedup group-bys and test the same canonical id present in two tenants in different states
- Match on the stable id at the identity's full uniqueness scope (document, not page); test moving content across partitions, editing matched attributes, and inserting/renumbering items
- Persist ids once into the source records and key outputs on (source, id)
