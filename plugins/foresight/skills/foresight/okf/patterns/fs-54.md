# FS-54 · Stored copy of a financial figure not re-derived when its source changes

Figures are persisted as copies of their sources: a header total (total_deposit, credit_card_total, purchase cost) beside its line items, a daily entry's stored total_in/total_out shown on the calendar, a leg's accounting_date copied from a CreditPayment, posted ledger rows the balance sheet reads instead of recomputing, M2M mirrors keyed on the old (org, location, date). Only some write paths re-derive the copy (an entity's own save() re-posts only its own legs), so edits, re-keys and merges leave copies stale; consumers reading the copy and consumers recomputing live disagree, and 'balanced after rebuild' decays.

**Triggers**
- a denormalized header/total field coexists with the child rows it summarizes, and different consumers read different ones
- a leg's date/account/amount is copied from a related object at creation time
- an edit to an entity drives legs that another process posted (no FK back to the entity)
- an update can change the key (org, location, date) a derived mirror or M2M link is keyed on
- a fix lives in save() and existing rows are expected to self-heal on the next rebuild; a merge edits posted legs but not the source pointer

**Guards**
- Derive totals from live child rows everywhere, or assert header == sum(lines) on save and run a periodic divergence query
- For every stored copy list each writer of its inputs and each leg it drives; re-derive on every path or recompute on read; test edit-source-then-read-ledger
- On key changes capture the old key before save and re-link/unlink both the old and the new key
- Fix the upstream source pointer (the FKs that regenerate legs), not only posted legs, and ship an explicit backfill when a save()-time fix must apply to existing rows
- Treat 'balanced' as a snapshot: schedule full-rebuild diffs for locations with ongoing edits
