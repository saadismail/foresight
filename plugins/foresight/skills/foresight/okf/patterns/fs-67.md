# FS-67 · On-device check runs a stale JS bundle or a dev-client path unlike the shipped build

On-device verification of an Expo/React Native fix runs code other than the edited source: Metro's transform cache or a quick rebuild serves the old transform, an Expo dev-client loads JS from its expo-updates store so an injected main.jsbundle is ignored (and a plain bundle injected into a Hermes release build crashes on launch), Fast Refresh patches a leaf but keeps parent closures holding old handlers, Metro restarted with CI=1 has Fast Refresh off, a warm dev-client drops Linking url events, and every full reload wipes in-memory auth. The old behavior reproduces and is read as 'the fix didn't work', or a pass is trusted on the wrong build. Mobile sibling of FS-02.

**Triggers**
- on-device behavior after a fix matches the pre-fix behavior exactly, even after a rebuild
- about to verify through a bundle-inject or 'fast rebuild' shortcut, or the installed app is an Expo dev-client rather than a release/embedded build
- the fix changes a handler captured in a closure (onSubmitEditing chain, ref callback, router handler) above the file just edited
- a subagent or script (re)starts Metro, possibly with CI=1 or other non-interactive flags
- testing a deep link (magic link, universal link) against an app that is already foregrounded in a dev-client
- several files will change during one on-device session in an app whose auth uses in-memory persistence (Firebase inMemoryPersistence)
- two consecutive code edits produce pixel-identical screenshots, especially after a simulator/device relaunch

**Guards**
- Before trusting an on-device result, prove the running bundle contains the change: grep the built/served bundle for a marker string unique to the new code, or restart Metro with --reset-cache
- Know the build type first: Debug dev-client -> iterate through Metro; release/embedded -> rebuild; never inject a plain JS bundle into a Hermes release build; clear .expo-internal / the updates store on dev-client builds
- After focus-chain, closure or router logic changes, force a full app relaunch instead of trusting Fast Refresh
- Forbid CI=1 when handing Metro to a subagent and confirm Fast Refresh with a trivial edit before trusting reload results
- Cold-start the app (force-quit, then open the link) when testing deep links against a dev-client so getInitialURL() handles them
- With in-memory auth, batch edits before a reload-triggering pass (or keep a persistent test session) instead of re-authenticating per edit
- Show a build/commit freshness marker in the UI (or check Metro's request log for this device) as step 1 whenever two edits look identical
