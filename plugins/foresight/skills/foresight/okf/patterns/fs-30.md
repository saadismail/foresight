# FS-30 · Working from a stale base or without checking existing work

A branch, worktree or audit runs against a snapshot that has fallen behind a fast-moving shared branch, or starts without checking whether the work already exists or is in flight. Overlapping edits, duplicate implementations and audits graded against the wrong code surface only at merge or review.

**Triggers**
- starting work on a ticket key or a hot shared file while other sessions are active
- a branch/worktree older than a few hours on a trunk receiving large refactors
- launching an audit/gap-analysis agent mid-session while others push
- consolidating via cherry-pick/rebase followed by push
- dispatching isolation:worktree agents right after committing on the orchestrator's branch; a cherry-pick conflict on a large, frequently edited file
- a new spec asserts a field's required/optional state while another merged ticket also touched that field

**Guards**
- Before starting: git fetch; git log origin/staging --grep <ticket>; gh pr list --search <ticket>
- Diff touched files against current origin/staging before substantive work and again before merge; cherry-pick feature commits onto the fresh tip
- Audit agents fetch first and log the origin SHA they graded; anchor every agent to its assigned worktree path
- Gate push on a clean rebase exit and a full build after consolidation
- Pin each worktree agent's base to an explicit branch/SHA and check it with git merge-base --is-ancestor before trusting its report; resolve hot-file conflicts with a 3-way merge (git merge-file), never --theirs/--ours, then grep for known recent fixes
- Read the field's current validation in the latest shipped code and requirement before asserting it
- After any scripted per-hunk ours/theirs resolution run eslint and tsc on every resolved file; prefer whole-file theirs for rewritten specs
