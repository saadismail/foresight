# FS-38 · Soft-deleted and terminal-state rows ignored by constraints and queries

Rows in deleted, archived or rejected states still participate in unique constraints, joins and aggregates, or their dependents are not cascaded: re-create after soft delete 500s on the unique constraint, Count() through relations bypasses the soft-delete manager, dedupe keeps a phantom row, SET_NULL parents un-hide children, deleting a bot leaves its membership seat, cascade restore via all_objects conflates batches. The default soft-delete manager hides only the queried model's own deleted rows, so rows under a soft-deleted PARENT still leak into counts, scoping helpers and eligibility checks.

**Triggers**
- the model uses SoftDeleteModel and has a unique/unique_together constraint or natural key
- an aggregate, annotation or join reaches a soft-deletable model
- deleting an entity that owns related rows (membership, synthetic user, children)
- a constraint meant as 'one active X' written as 'one X ever'
- a get-or-restore or create path that revives a soft-deleted row a merge deliberately removed; callbacks that can write to a terminal-state task
- a serializer inlines a Prefetch of a soft-deletable model in a payload that an offline-sync pull persists to devices
- a scoping helper, count, aggregate, retry-eligibility check or service method that reaches a row whose PARENT (project, document, page, ticket) is soft-deletable
- a tenancy resolver or helper that uses all_objects, or a service that accepts model instances resolved by another caller (bot approve path)
- a decision/resolution workflow whose every option dereferences user-deletable content, or a new dependent table under an existing unlink/delete path
- re-entering work through a chat/run thread whose session already completed
- an automated handoff or reassignment to a stored person (reporter, owner, creator) who may have left the workspace since

**Guards**
- Test soft-delete then re-create with the same key; look up all_objects by natural key and revive before create
- Add filter=Q(is_deleted=False) to aggregates and compare list vs detail counts
- Use conditional unique constraints scoped to active status; cascade soft-delete to children with a batch id
- Test deleting the parent and assert dependent rows/seats are released
- Check the merge log and deletion reason before reviving; reject writes to terminal states
- Filter deleted_at in every Prefetch/inline queryset of a soft-deletable model and add a sync test that a soft-deleted child disappears on the other device
- Lane 0: write a parent-chain table of every entity and its soft-deletable ancestors (e.g. project -> document -> page -> section; project -> ticket -> link) with the filter each query and aggregate must add (page__is_deleted=False, project__deleted_at__isnull=True); every brief cites it
- Test every aggregate, scoping helper and eligibility check with a soft-deleted PARENT (not only a soft-deleted row) and assert exclusion; services re-check liveness of passed instances and their ancestors
- Give every decision that dereferences deletable content a fallback resolution, and extend the existing delete/unlink path whenever a dependent table is added
- Treat completed sessions as terminal: re-entry starts a new round, never resumes a finished one
- Test each automated assignment with a departed member and decide the fallback (skip, reassign, escalate) instead of letting a validation error roll the transition back
