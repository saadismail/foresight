# FS-103 · Column or renderer definitions rebuilt from volatile inputs remount the subtree

A table or list derives its column definitions, cell renderers or component types from volatile inputs (viewport width read in JS, a timer or flash state, inline handlers). When an input changes, even transiently, the UI framework sees new definition identities and remounts every cell, so local state inside them (an open menu, focus, an edit in progress) is dropped. Human testing at one stable width passes; resize events, transient layout values or a parallel suite surface it.

**Triggers**
- column defs, cell renderers or component types computed inside render or memoized on viewport width, flash/timer state or inline callbacks
- a JS width or matchMedia check choosing which columns or layout a table renders
- an open menu, popover or inline editor that lives inside a table cell

**Guards**
- Switch layouts with CSS breakpoints instead of JS-chosen column sets
- Keep column and renderer definitions identity-stable (module scope or memo with stable deps) and pass volatile values and handlers through context, table meta or refs
- E2E: open the in-cell menu, fire a resize (including a transient tiny width) or the data/timer change, and assert the menu stays open
