# FS-65 · Which host, checkout or branch serves an environment assumed

Boxes keep a manual git checkout beside the CodeDeploy-served directory, services track a branch other than the one just pushed, a staging hostname hits the dev backend while sharing the prod DB, and only one box ships logs to the central store. Verification, restarts, migration checks and forensics run against whichever host or directory is at hand and produce clean-looking but wrong answers ('deployed', 'no logs', 'migrated').

**Triggers**
- verifying deployed code or migration state on a box, or advising 'restart to pick up the change'
- searching a central log store for a non-prod hostname's traffic
- installing a long-running service against an ad hoc checkout while the pipeline is blocked
- about to conclude that evidence or logs are unrecoverable
- a prod manage.py run after sourcing .env.prod without --settings or an exported DJANGO_SETTINGS_MODULE

**Guards**
- Read the service's systemd unit WorkingDirectory and venv, then check git -C <that dir> rev-parse HEAD and its branch before verifying or restarting
- Confirm which backend host serves each hostname and whether its logs ship before searching; enumerate known hosts (deploy config, DNS, known_hosts) before declaring data unrecoverable
- Track any service pointed at a manual checkout as temporary and re-point it at the deploy target before calling the rollout done
- Pass --settings explicitly and print the resolved settings module and DB host as the first output line of any prod ops command
