# FS-24 · Pushed, merged or deployed state assumed instead of checked

Work is reported merged, deployed or live because it was pushed, because automation (auto-PR/automerge, deploy-on-merge) usually fires, or because memory says so. The automation silently didn't run (branch already existed, Actions budget exhausted), the fix sits unmerged in a worktree, or only staging got it while the verifier checks prod.

**Triggers**
- about to tell the user 'merged', 'deployed', 'live' or 'shipped'
- pushed a claude/* branch expecting automerge, or merged to staging expecting auto-deploy
- memory or a prior session claims a fix already landed
- the instruction says 'deploy' but no deploy command for that environment is known
- a revert on one branch while the fix already promoted elsewhere; a branch prefix vs the workflow trigger glob; a merged fix not live because an unrelated broken build blocks deploy

**Guards**
- Verify with git ls-remote / gh pr list / gh run list for the exact SHA and confirm origin/<base> contains the commit
- Check the deployed artifact on the exact domain the verifier uses (asset hash, endpoint response)
- State git, PR and deploy status explicitly in every done report ('pushed only' when that is the truth)
- Read .github/workflows before assuming automation behavior
- Run git branch -r --contains <sha> on every promoted branch; check the environment's CI build history and the deploy system's deployment log, not process uptime
