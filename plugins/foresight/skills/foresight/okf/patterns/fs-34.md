# FS-34 · Nondeterministic test timing and ordering

Tests race the app or each other: waitForResponse registered after goto, reload before the mutation response lands, smooth scroll vs actionability, skeleton assertions against same-tick stubs, hover/drag under parallel workers, headless dnd coordinates, real clock vs fixed fixture dates, order-dependent DB or polyfill leakage between tests. Failures move between runs and get misread as regressions.

**Triggers**
- a spec triggers a navigation/mutation and then waits for its network response
- drag/hover interaction specs in a suite with parallel workers
- date-specific fixtures without page.clock, or loading-state assertions against stubs
- a different single test fails each full run but every file passes alone
- a date-picker spec clicks a testid embedding a literal ISO date; a transition-class assertion right after a navigation that remounts the wrapper; Escape sent right after opening a dialog whose handler is dialog-scoped
- a driver closes a Radix menu/popover/dialog and immediately clicks another trigger, types, or sends Escape while the closing overlay is still mounted for its exit animation or returning focus
- changing the runtime under an e2e suite (Vite dev -> production build, cold vs warm dev server, more workers, faster backend): specs that sampled an intermediate state or used a fixed 10 s expect timeout were calibrated to the old speed
- a driver that moves a ProseMirror/BlockNote caret and presses a key as soon as the DOM selection moves; UI state hydrated from a server preference that a spec toggles and reloads
- an e2e step clicks outside a Radix/headless overlay right after opening it (outside-pointer listeners are armed a tick after open)
- a query-count test compares two requests on a fresh connection while the app has per-connection probes or process-level caches; a test that passes in the full run but fails alone

**Guards**
- Register waitForResponse before the triggering action and await mutations before any reload
- Pin page.clock for date fixtures; run drag/hover specs serially and prove the logic with a unit test
- Rerun suspects standalone twice and treat 'different failure each run' as isolation leakage (polyfills, DB cleanup)
- Compute dates relative to a pinned page.clock and page the calendar to the target month; poll for the incoming node (route-scoped id or last()) across remounts; wait for focus inside the dialog before sending dialog-scoped keys
- Every driver close helper waits for the overlay (role=menu/dialog, radix popper wrapper) to detach and focus-return to finish before the next interaction; never click a trigger while another overlay is mounted
- Before switching runtime or worker width, grep specs for networkidle, toHaveURL on intermediate routes and fixed sleeps, assert only final settled state (a route-ready testid), warm the dev server before the setup project, and require 3 green runs at the new width with an isolated control
- Poll the editor's own state (view.state.selection) and wait on the concrete GET/PUT of server-hydrated preferences before the next key or reload; run every touched spec with --repeat-each=3 before commit
- Wait for the overlay's open state and a frame before the outside click, or poll for dismissal; prove with --repeat-each 4
- Make one untimed warm-up request with the same URL shape on the same data before counting, and run every new test alone in a fresh process as well as in the parallel full run
