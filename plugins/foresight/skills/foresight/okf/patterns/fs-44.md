# FS-44 · Migration unsafe for code or data already in the shared DB

A migration is right for the new code but not for what already exists: NOT NULL columns without db_default applied to a DB shared with older deployed code or parallel agents, constraints older code violates, role/RLS DDL needing privileges the app user lacks, raw SQL without cross-app dependencies, behavior flips with no backfill for existing rows.

**Triggers**
- a new NOT NULL column or DB constraint on a table staging and prod share
- a migration with raw SQL on another app's table, or role/privilege DDL
- a feature flips an enablement flow for rows created under the old flow
- staging and prod share one DB and the change alters the shape of rows (nesting, new parent links) that the deployed prod code also reads or writes

**Guards**
- Set db_default (or nullable + backfill) for new required fields; run sqlmigrate and reject bare ADD COLUMN NOT NULL on shared tables
- Confirm every currently deployed code path honors a new constraint before it reaches the shared DB
- Check rolsuper/CREATEROLE of the target DB role, and declare explicit cross-app migration dependencies
- Ship a backfill with any behavior change and test it on pre-existing rows
- Make the deployed code tolerate the new row shape first, or schedule the prod deploy right after staging; test the old code path against new-shape rows
