# FS-93 · Live service config edited without a parse check and a post-restart re-read

Config for a running service is changed on a host and assumed to take effect and persist, whether through ALTER SYSTEM, a conf.d drop-in or postgresql.conf edited by an inline ssh command. A double-quoted value fails to parse and the server won't start. Nested quoting across ssh silently mangles the file. An ALTER SYSTEM value is lost when a package install triggers needrestart and bounces the service. The fallout appears later as 'database unreachable' and looks like an unrelated regression.

**Triggers**
- writing a service config value via echo/heredoc or an inline ssh/sudo command with nested quotes
- ALTER SYSTEM or another runtime-only setting followed by apt installs or other steps that can restart the service
- a migration or provisioning session making several config edits on a production host in sequence
- a secret written into .env as KEY=value #comment (unquoted inline comment on the value line), or any env value whose loader comment and quote rules are unverified

**Guards**
- Write config through a script file or a drop-in copied to the host, not multi-layer quoted inline commands
- Validate before restarting with the service's own checker (postgres -C <setting> --config-file, nginx -t, a foreground start) and use the config language's quoting (single quotes in PostgreSQL)
- Persist settings durably (conf.d drop-in) and re-read the effective value (SHOW <setting>, a health check that touches the DB) after every later install or restart step
- Diff a failing ad hoc run against the verified harness path before trusting its failure count
- Assert each loaded secret's length/prefix at startup (log the length, never the value) and lint .env files for text after the value before deploying
