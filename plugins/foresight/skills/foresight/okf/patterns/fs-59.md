# FS-59 · Model save() side effects unknown to the caller

Domain models override save() to auto-create or recompute related rows (Check.save() creates an Expense when expense is None and recomputes a linked purchase entry, Transaction.save() syncs the ledger entry, hooks re-query relations through custom managers). Callers that haven't read save() double-create rows in fixtures, spawn duplicates when linking FKs via save(), treat re-save as an idempotent restore, trigger the same recompute three times, assume an invariant the hook breaks, compare against an in-memory instance the update already mutated, or pass _id so the hook's re-query misses an uncommitted parent.

**Triggers**
- calling .save() on a model with an overridden save() or signals from a script, fixture, rebuild or relink step
- designing a match/link rule that assumes a related object is usually absent
- a save()-time guard that inspects a field the same update may change
- creating parent and child in one atomic block and assigning the FK by _id
- adding a hook that calls a function other hooks already call

**Guards**
- Read the model's save()/signal chain before writing fixtures, rules, scripts or hooks that touch it, and assert related-table row counts before/after a dry run
- Link FKs with queryset.update() when save() side effects are unwanted; assign the related object, not _id, when save() re-reads the relation
- Capture previous values from the DB (not the mutated instance) for save()-time cleanup guards
- Don't use re-save as a restore unless save() replays stored values; add a call-count test for recomputes per save
