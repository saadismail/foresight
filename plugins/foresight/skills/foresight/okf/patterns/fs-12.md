# FS-12 · Deploy pipeline doesn't carry or match what the change needs

The change depends on infra the deploy doesn't provision or sync (nginx location, worker/beat unit, firewall port, env var, cache headers), or the live host has drifted from the repo (hand patches, root- or CI-user-owned files, wrong gcloud account, FE bundle built from the wrong branch, builds on the shared prod VM). The code is correct but the environment silently doesn't run it.

**Triggers**
- the diff adds a URL prefix, route, service/port, Celery task or env var
- the deploy script only reloads nginx/services instead of installing repo config
- manual deploy on a host where CI previously ran as another OS user, or after a Docker-to-native cutover
- local-build-then-ship FE deploy, or staging and prod sharing one host
- a feature adds a Django migration while the target's deploy (CodeDeploy) skips migrate; a deploy hook deletes everything except an allowlist; an env var used by several systemd units; a log path change
- changing a Secret-Manager-backed variable or a settings default on a VM that may also carry a local .env; rotating a secret that the service reads only at boot
- settings call environ.Env.read_env() on a fixed path while deploy.sh sources the .env into the shell; a DB server provisioned on a network with a broad existing firewall rule for its port
- the diff edits the deploy script that will run this very deploy (the shell executes the copy loaded before git pull)
- a Node entry point calls dotenv.config() with an implicit relative path and the repo holds more than one .env file
- a host migration rebuilds a venv from requirements files on a box whose old venv had hand-installed packages; several env files (admin.env, portal.env) define the same DB credential
- a deploy step restores a built entrypoint from git (git checkout -- dist/index.html) instead of rebuilding, on a host where nginx serves dist/ directly; the step comes from a remembered 'standard flow' of an earlier session
- a provider API key (SendGrid, SMTP2GO) is rotated or first set in prod and judged working because it authenticates
- periodic or scheduled work (a Celery beat entry, a cron line) added for hosts whose deploy runs only web units and systemd timers (recurs: a scheduled sync and later an alert were both wired to a scheduler no host runs)

**Guards**
- For every new route/port/unit/env var, confirm the deploy script installs it and curl the real public path after deploy
- Diff the live nginx/env config on the box against the repo before debugging routing; commit or remove hand patches
- Chown deploy dirs to the deploying user and pin the gcloud account before starting
- Build the FE from an explicit checkout of the target ref and verify the served asset hash; never build on the prod box (SKIP_FE_BUILD=1)
- Run showmigrations / migrate --plan on the target box after any deploy carrying a migration; provision env vars into every unit that calls the helper; add a post-deploy health check that fails the pipeline
- grep the live VM's .env for the same key and confirm the runtime value after restart with an authenticated request; restart every consumer right after rotating a boot-time secret
- Put or symlink the .env where the library reads it as the first deploy step and run deploy.sh end to end; after provisioning, probe the DB port from outside the VM and grep postgresql.auto.conf for listen_addresses
- After changing the deploy script, re-exec it after git pull or run the new step explicitly, then verify each new step's effect (query the role/table it creates) rather than a green health check
- Log the resolved .env path and injected-variable count at boot, and confirm the process cwd before editing a live server's env
- Before a host migration diff pip freeze on the old host against every requirements file; confirm which env file the running unit loads before provisioning a DB role, then smoke-test the real end-to-end login
- Rebuild dist/ as part of the deploy, never git checkout build output, then fetch / and every asset hash it references and require 200
- After rotating a provider key, fire one real call of the exact operation (send a test email) and read the key's scope list from the provider's key-info endpoint; alert on send failures rather than only logging them
- Before wiring periodic work, read which scheduler the target hosts actually run (systemctl list-timers, the deploy's unit files) and register the job there; a test or deploy check asserts that scheduler invokes the entrypoint
