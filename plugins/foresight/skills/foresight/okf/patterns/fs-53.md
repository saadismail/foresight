# FS-53 · Known fix or learned rule not made durable, so the same trap recurs

A root cause is found and fixed on a branch, filed as a chip, or taught by the user, but never carried to where it stops recurring: the fix sits unpromoted at some hop of the promotion chain (or pushed with no PR), the filed durable fix is never implemented, a pending migration is never landed, a faster tool or new safety rule never reaches the skill's default recipe or the scripts already written. The symptom keeps firing in production and is hand-healed, costing a round each time.

**Triggers**
- the same symptom class shows up a second time, or a manual cleanup/sweep is being run again
- a fix was 'pushed' but no promotion PR is open, or it has not reached main
- a chip/TODO for the durable fix already exists for the error you are re-patching
- the user states a rule correcting a mistake, or a new tool supersedes the documented recipe
- every branch has to detect-and-ignore the same drift (unmade migration, scanner false positive)
- a release helper or upload fix being recreated ad hoc for the second time; a session ending with a diagnosed fix deliberately held back
- the same failure is flagged 'pre-existing, not my change' in two or more sessions
- a process gap hit once in a parallel batch while other tickets in the same batch are still queued

**Guards**
- On the second occurrence treat the root-cause fix as blocking: report its branch -> PR -> promotion stage and count only 'merged to main and deployed' as done
- Keep one visible list mapping recurring bug classes to fix branches and their promotion stage, and surface it every time the class fires
- Write a user-taught rule or a new default tool into the skill/runbook immediately, then grep previously written fix scripts for violations
- Land shared drift fixes (pending migration, scanner excludes, allowlists) once on main instead of working around them per branch
- Commit hardened helpers into scripts/ on the first fix; write a held-back diagnosis and its next action to a ticket or memory before the session ends
- Once a failure is confirmed pre-existing twice, fix it or file and link a ticket instead of re-flagging it
- Add the learned step to every remaining brief and reviewer checklist in the batch immediately
