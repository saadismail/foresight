# FS-108 · Non-production deploy acts on production data through a shared store

Staging and production share one database, queue or outbox, so any worker, sweep or drain deployed to staging runs against production rows and posts to production integrations (chat, email, webhooks). A new sweep designed as if it runs only at the production deploy releases an accumulated backlog, such as weeks-old messages, to real users the moment staging deploys. Tests run on an isolated DB, so the cross-environment reach shows up only in review or in production.

**Triggers**
- a new worker, sweep, drain or reconcile job over a table, queue or outbox that more than one environment reads
- the first run of a new sweep over rows that accumulated before it existed
- an environment whose settings point at another environment's database, broker or integration credentials

**Guards**
- Before shipping a worker, list every environment that runs it against the same store and every external endpoint it posts to; gate its side effects to the environment that owns the rows (an environment flag or an owner column)
- Bound the first run: dry-run count the rows it would act on, skip items older than a cutoff, and release any backlog deliberately
