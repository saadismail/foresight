# FS-57 · Reconciliation tooling re-implements production posting logic and drifts

Verify, resync, drift-detection and fast-check commands carry their own copy of which entities post which legs: a filter narrower than save()'s dispatch conditions, a step list missing helper calls the real view makes, a sync wired to one of two models behind a UI bucket, a mirror query without the reference's organization filter, counterpart lookups limited to the audited subset, exclusions encoding a rule a later feature changed, a rebuild that posts directly instead of calling save(). The tool's output then disagrees with production and is misread as a production bug or as a clean bill of health.

**Triggers**
- writing or extending a verify/resync/detector command, or a 'fast' helper meant to mirror an authoritative computation
- the tool calls service posting functions directly instead of the entity's save()/view flow
- a feature changes what a source_type posts while detectors special-case that type
- a detector resolves relationships from within its own filtered queryset

**Guards**
- Diff the tool's step and filter list against every ledger-posting call reachable from the entity's save()/view flow; reuse save() or the same service entry point instead of a partial copy
- Assert equality with the reference computation over a swept historical range (including foreign-org and duplicate-leg data), not a hand-picked sample
- Resolve counterparts against the full table, not the audited subset
- When shipping a posting change, grep every reconciliation predicate that special-cases the source_type and add a regression test
