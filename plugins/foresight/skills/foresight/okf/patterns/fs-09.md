# FS-09 · Green signal whose scope doesn't cover the claim

A check reports success without observing the claimed property: CI that lints but never builds or tests, tsc --noEmit on a references-only root, e2e files outside the type-check, a 302/200 probe answered by an SPA fallback, curl http_code on a WebSocket upgrade, a stale CI badge, a suite run before the last change, a fabricated RED step, proof screenshots overwritten or misleading. The claim ships on the strength of the signal.

**Triggers**
- about to report 'verified' or 'green' from a status code, redirect, CI badge or a scoped/filtered run
- the type-check/lint command differs from the project's real build command (npm run build / tsc -b)
- another change landed after the last full verification run
- proof screenshots written into test-results/ or a docs/qa path other runs also write
- reporting a location balanced from a dry run over stored ledger rows, a single-day detector, a job's exit code, or a balance-sheet delta of 0
- declaring an infra cutover or deploy done from a /health endpoint that doesn't touch the DB; reporting a multi-leg pipeline (store SDK -> backend -> app UI) as 'verified on device' after injecting synthetic data for one leg
- a raw CSS edit checked only under the dev server/HMR; a completeness audit narrating another actor's capability; resuming another session's ticket where RED logs and screenshots already exist; a full-suite run that rewrites tracked screenshots of unrelated specs
- the only validator reachable in a worktree without node_modules is node --check on a JSX/ESM file
- an xcodebuild/gradle smoke build run without an explicitly named scheme/target and judged by exit code 0
- an animation timing value copied from a design board (stagger under ~150ms) reported done without watching it run
- specs that call page.screenshot({ path }) with a path inside a tracked QA-docs folder, overwriting tracked files, run by a full or sharded suite
- deciding pass/fail by grepping a test runner's colored output for a summary line ('N failed', 'N passed')
- a requirement or ticket marked green from a scoped test run

**Guards**
- Run the exact project gate (npm run build, scoped pytest for touched apps) as the last step after the final change
- Probe the actual property end to end: POST reaches the backend, WS returns 101 via curl -v, OAuth round-trips through the real proxy
- Confirm the gate runs at all: CI has build/test jobs without continue-on-error, e2e specs are in the type-check include, a canary failure blocks
- Copy proof screenshots to a unique dir immediately and git status for clobbered docs/qa files before committing
- Re-run the authoritative full-range check (full rebuild / day_delta walk) and confirm expected source types (opening balances) are present before saying balanced
- After cutovers hit one authenticated, DB-touching endpoint end to end and make health checks touch the DB; report verification per leg (real data / injected / unit test only)
- Run the production build (next build) after CSS edits and before every deploy; cite a file:line in that actor's own code for each journey step; re-run the target suite before estimating remaining work; stage only the current change's own proof screenshots
- Sanity-test any fallback validator against deliberately broken input before trusting it; treat node --check as no signal for JSX and use a real parser (esbuild/babel/eslint, or the main tree's node_modules)
- Print and assert the built scheme/target and the expected output artifact, not just the exit code
- Watch timed or staggered animations at runtime (screen-record or slow-mo) and map spec values to perceptible motion tokens before calling them done
- Write run screenshots to testInfo.outputPath() and copy into the tracked QA-docs folder only in a deliberate proof step; run git status on that folder after every full run
- Strip ANSI escapes first (sed 's/\x1b\[[0-9;]*[A-Za-z]//g') or use a machine reporter (JSON/JUnit), then read the list of failed specs, not just the count; treat 'no match' as unknown, not green
